# ADR-0040 — Secret providers : trousseau OS et vault fichier AES-256-GCM

## Statut
Accepté

## Contexte

Après Docker ([ADR-0039](0039-image-docker-multi-stage-distroless.md)), Lucas a choisi le secret provider comme chantier suivant de la Phase 6 : jusqu'ici `secrets.EnvStore` (variables d'environnement) est le seul adaptateur `secrets.Store` du dépôt. L'ADR-0020 avait déjà anticipé cette dépendance : `Reference.Type` sert de clé de routage vers un adaptateur, `ValidateType` n'autorisait que `"env"` en attendant "les autres adaptateurs listés en section 15.3 du document de vision" (trousseaux OS, HashiCorp Vault, fichiers Docker secrets...), et sa section "Conséquences négatives" prévenait explicitement qu'une variable d'environnement n'est "pas suffisant pour un déploiement serveur multi-utilisateurs sans un adaptateur plus robuste (Keychain/Vault) d'abord".

Contrainte explicite de Lucas : pas de dépendance à un service cloud, pour des raisons de gouvernance des données — élimine HashiCorp Vault (au moins en mode serveur distant) et tout coffre-fort géré. Deux adaptateurs locaux couvrent les deux formes de déploiement du produit (non-négociable #2 : même binaire local et serveur) :

- **`keychain`** — le trousseau natif de l'OS (macOS Keychain, Windows Credential Manager, Linux Secret Service), pour l'usage local-first.
- **`file`** — un vault fichier chiffré, pour le déploiement serveur/Docker, où il n'existe généralement pas de trousseau OS accessible (conteneur headless).

## Décision

**`MultiStore` remplace le choix d'un provider global.** `internal/secrets/multistore.go` introduit `type MultiStore map[string]Store`, qui route `Resolve` par `Reference.Type` vers l'adaptateur enregistré sous ce type. Ce n'est pas un remplacement d'`EnvStore` par un autre choix unique : les trois adaptateurs (`env`, `keychain`, `file`) coexistent, et quel adaptateur résout une référence donnée est une propriété de cette référence, pas un réglage global de l'agent — exactement le modèle qu'ADR-0020 avait laissé ouvert. `secrets.BuildStore(dataDir, masterKeyFile)` assemble ce `MultiStore` une fois, au même endroit pour tous les points d'entrée qui résolvent des secrets (`internal/runtime.NewAgent` pour l'agent qui tourne, les commandes `internal/cli` qui touchent connecteurs/secrets/workflows directement) — CLI et API passent par la même construction (non-négociable #8). `ValidateType` accepte désormais `"env"`, `"keychain"`, `"file"` ; comme pour `"env"` avant cette passe, la validité syntaxique d'un type reste indépendante du fait que cet agent ait effectivement configuré l'adaptateur correspondant — un connecteur `--secret x=file:KEY` peut être créé avant même qu'un master key file existe.

**`file` : AES-256-GCM sur un seul fichier, sans KDF.** `internal/secrets/file.go`. Le vault est un fichier JSON `{"nonce":"...","ciphertext":"..."}` où le ciphertext scelle l'intégralité d'une `map[string]string` (nom logique → valeur) — pas un chiffrement entrée par entrée : `Set`/`Remove` déchiffrent, modifient la map, rechiffrent avec une nonce fraîche (`crypto/rand`) et réécrivent tout le fichier, atomiquement (fichier temporaire + `os.Rename` dans le même dossier). La clé maître doit faire exactement 32 octets (AES-256 direct) — **pas de dérivation de clé/passphrase** : elle est censée être générée par machine (`patchcord secret keygen`, `crypto/rand`), jamais choisie par un humain, donc rien à étirer. `FileStore.Resolve` relit et déchiffre le fichier à chaque appel plutôt que de garder les secrets déchiffrés en mémoire — coût disque négligeable contre une surface d'exposition mémoire réduite, décision révisable si la fréquence de résolution devient un problème réel.

**La clé maître ne vit jamais à côté du vault.** Elle est fournie via `--secrets-master-key-file` / `PATCHCORD_SECRETS_MASTER_KEY_FILE` / `secrets_master_key_file` (même couche de précédence qu'ADR-0038) — un fichier, jamais une valeur en `--flag` ou visible dans une variable d'environnement classique (`/proc/<pid>/environ`, `docker inspect`), pour rester compatible avec la convention Docker secrets. Le chemin du vault lui-même n'est pas configurable séparément : fixé à `<data-dir>/secrets.vault`, à côté de la base SQLite qui vit déjà dans `DataDir` — un point de configuration de moins.

**`keychain` : `github.com/zalando/go-keyring`, un service fixe.** `internal/secrets/keychain.go`. Bibliothèque choisie parce qu'elle ne tire aucune dépendance cgo (vérifié après `go get` : `security` en sous-processus sur macOS, appels wincred sur Windows, D-Bus pur Go via `godbus/dbus/v5` sur Linux) — compatible avec le binaire unique et l'image Docker distroless sans base libc (ADR-0039). Tous les secrets `keychain` de cet agent vivent sous le même `Service` (`"patchcord"`, constante `secrets.KeychainService`) — pas de configuration, un agent a un seul namespace de trousseau. **Limite connue et documentée, pas un bug** : un conteneur Linux headless n'a généralement pas de démon Secret Service — `keychain` fonctionnera en local (poste de dev, agent desktop) mais échouera à la résolution dans la plupart des déploiements Docker/serveur ; `file` est l'adaptateur recommandé dans ce cas.

**Écriture des secrets : `patchcord secret {keygen,set,remove}`**, `internal/cli/secret.go` — ressource indépendante de `connector create`, puisqu'un même secret (`file:PG_PASSWORD`) peut être référencé par plusieurs connecteurs. Comme `connector`/`auth token`, ces commandes touchent directement le vault fichier ou le trousseau OS, jamais via HTTP (ADR-0036 avait déjà posé ce principe pour le tout premier jeton admin, avant qu'une authentification API n'existe). `secret set` lit la valeur **depuis stdin**, jamais un flag ni un prompt interactif masqué : un flag finirait dans l'historique shell et `ps`, et un prompt masqué aurait exigé une nouvelle dépendance (`golang.org/x/term`) pour un gain marginal face à `printf '%s' "$X" | patchcord secret set --type file KEY`, déjà scriptable. `secret keygen` imprime une nouvelle clé maître aléatoire sur stdout, sans effet de bord — à rediriger par l'opérateur lui-même.

**Exclusions de scope explicites** :
- *Pas de `secret list`* : `go-keyring` n'expose pas de listing portable par service (les trousseaux natifs ne l'offrent pas uniformément), et n'implémenter le listing que pour `file` casserait la symétrie entre les deux adaptateurs.
- *Pas de rotation de clé maître* pour `file` : changer de clé aujourd'hui impose de déchiffrer avec l'ancienne et réécrire secret par secret via `secret set` — pas de commande dédiée.
- *Pas de dérivation de clé/passphrase* (KDF) — voir plus haut, choix délibéré tant que la clé reste machine-générée.
- *HashiCorp Vault* reste hors scope, conformément à la contrainte de gouvernance des données de Lucas ; rien dans ce modèle (`Store`, `MultiStore`) n'empêche de l'ajouter plus tard comme adaptateur supplémentaire si le besoin apparaît.

## Conséquences positives
- Ferme le renvoi qu'ADR-0020 avait laissé ouvert, avec un modèle (`MultiStore` par type) qui n'oblige à choisir qu'un seul provider global — trois adaptateurs coexistent nativement.
- Aucun appel réseau, aucun compte, aucun service tiers requis pour chiffrer/déchiffrer un secret — conforme au non-négociable #9 et à la contrainte de gouvernance de Lucas.
- CLI et agent construisent le store exactement de la même façon (`secrets.BuildStore`) — pas de logique dupliquée (non-négociable #8).
- Zéro changement de comportement pour l'existant : tous les appelants qui construisaient `secrets.EnvStore{}` en dur (API, runner de workflows, scheduler, CLI) retombent sur `EnvStore{}` par défaut si aucun store n'est explicitement câblé — les ~50 tests existants qui construisaient `Deps{DB: db}`/`ExecuteOptions{}` sans s'en soucier n'ont eu besoin d'aucune modification.

## Conséquences négatives
- `file` sans KDF signifie qu'une clé maître compromise (fichier `--secrets-master-key-file` mal protégé) expose tout le vault d'un coup — pas de compartimentation par secret. Acceptable pour un vault dont le rôle est déjà "protégé par les permissions du fichier hôte", pas un remplacement d'un vrai HSM.
- `keychain` échoue silencieusement (à la résolution, pas à la validation) sur la plupart des déploiements Docker/serveur — un opérateur qui configure un connecteur avec `--secret x=keychain:KEY` sur un agent serveur ne le découvre qu'à l'exécution, pas à la création du connecteur (même limite déjà acceptée pour `env` par ADR-0020).
- Pas de rotation ni d'audit d'accès pour aucun des deux adaptateurs — cohérent avec le stade "adaptateur de démarrage" déjà assumé par ADR-0020 pour `env`, mais toujours à ne pas présenter comme suffisant pour un déploiement multi-utilisateurs exigeant.
- `FileStore` relit et déchiffre tout le fichier à chaque `Resolve` (pas de cache) — un run avec beaucoup d'étapes liées à des connecteurs `file` paie ce coût à chaque résolution ; négligeable à l'échelle actuelle, à revisiter si ça devient mesurable.
