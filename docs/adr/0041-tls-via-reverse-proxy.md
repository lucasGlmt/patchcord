# ADR-0041 — TLS via reverse proxy, jamais dans le binaire

## Statut
Accepté

## Contexte

Dernier chantier de la Phase 6 après la configuration serveur ([ADR-0038](0038-configuration-serveur-fichier-yaml-precedence.md)), Docker ([ADR-0039](0039-image-docker-multi-stage-distroless.md)), les secret providers ([ADR-0040](0040-secret-providers-keychain-et-fichier-aes.md)), l'authentification admin ([ADR-0036](0036-authentification-admin-jetons-opt-in.md)) et le trigger webhook ([ADR-0037](0037-trigger-webhook-secret-partage.md)).

Le document de vision ne laisse pas d'ambiguïté sur ce point (§13.4, §15.2) : "Patchcord peut être installé derrière un reverse proxy [...] TLS", listé aux côtés d'OIDC, d'un pare-feu, "une infrastructure d'entreprise" — des mécanismes que l'agent suppose déjà en place autour de lui, pas qu'il implémente. La roadmap (§19, phase 6) confirme : l'item s'appelle explicitement "TLS via reverse proxy", pas "TLS". `internal/api.NewRouter` (vérifié dans le code) n'a jamais fait d'hypothèse sur le transport — `internal/runtime.Agent` sert sur un `net.Listener` TCP nu, sans branchement `http.ServeTLS` nulle part. Aucune logique du core ne dépend non plus d'un `RemoteAddr`/`X-Forwarded-*` (vérifié : aucune occurrence dans `internal/`) — l'authentification admin est un jeton porteur (ADR-0036), pas un contrôle par IP, donc rien à adapter côté Go pour accueillir un reverse proxy devant l'agent.

## Décision

**Aucune terminaison TLS dans le binaire Go.** `serve` continue de servir en HTTP brut, sur `127.0.0.1` ou `0.0.0.0` selon la configuration (ADR-0038) — pas de flags `--tls-cert`/`--tls-key`, pas de dépendance à `crypto/tls` au-delà de ce que `net/http` embarque déjà pour les appels clients. Ajouter un stack TLS complet (gestion de certificats, renouvellement, ACME) au core violerait l'esprit du non-négociable #1 (l'agent doit rester utilisable sans dépendance à un mécanisme lourd) pour un problème déjà bien résolu à la couche reverse proxy — dupliquer cette responsabilité dans le core irait à l'encontre de "le core fournit les mécanismes" (CLAUDE.md §0) en ajoutant un mécanisme que l'écosystème (Caddy, nginx, Traefik, load balancers cloud) fournit déjà, en mieux.

**Exemple de référence : Caddy, HTTPS automatique**, choisi par Lucas parmi les options (Caddy vs nginx+certificats manuels vs les deux) pour sa simplicité — un Caddyfile de trois lignes suffit à obtenir et renouveler un certificat Let's Encrypt via ACME, sans étape manuelle. `docker-compose.tls.yml` (racine du dépôt) : le service `caddy` publie `80`/`443`, monte `docker/Caddyfile` et deux volumes nommés (`caddy_data`, `caddy_config`, pour persister le certificat entre redémarrages) ; le service `patchcord` ne publie plus rien vers l'hôte (`expose: ["7331"]` seulement), joignable uniquement par `caddy` sur le réseau Docker interne. `PATCHCORD_DOMAIN` est une variable d'environnement requise (`${PATCHCORD_DOMAIN:?...}` — Compose refuse de démarrer sans elle, avec un message explicite plutôt qu'un Caddy qui échouerait obscurément à l'obtention du certificat) : aucune valeur par défaut n'a de sens ici, contrairement à `--listen`/`--data-dir` (ADR-0038).

**Pas de service cloud ni de compte tiers requis pour les données elles-mêmes** (contrainte de gouvernance de Lucas, déjà appliquée à l'ADR-0040) : Let's Encrypt via ACME est une validation de domaine standard, sans compte à créer ni donnée applicative transmise — différent en nature d'un secret provider géré. Un opérateur qui ne veut aucun appel réseau sortant, ou qui n'a pas de domaine public (déploiement interne/offline), peut mettre n'importe quel reverse proxy déjà en place devant `patchcord serve` de la même façon (proxy vers son adresse HTTP brute) — documenté dans `docs/book/src/cli/serve.md`, pas un deuxième exemple Compose maintenu en parallèle : la variation ("nginx + certificats fournis") n'a pas été retenue comme fichier séparé pour éviter deux configurations Compose à maintenir en synchronisation pour un seul point (l'outil de terminaison TLS), alors que le principe ("reverse proxy devant, `patchcord` n'écoute qu'en HTTP") est identique et déjà couvert par l'exemple Caddy.

**Rappel explicite dans la doc, pas dans le code** : TLS protège le transport, pas l'accès — créer un jeton admin (ADR-0036) reste une étape séparée et toujours nécessaire avant d'exposer `serve` derrière un domaine public. `docs/book/src/cli/serve.md`'s section "TLS" pointe vers "Admin authentication" pour cette raison plutôt que de la répéter.

## Conséquences positives
- Ferme le dernier point de la Phase 6 sans ajouter de complexité ni de dépendance de gestion de certificats au core — cohérent avec le non-négociable #1 et avec le principe "le core fournit les mécanismes" (CLAUDE.md §0).
- L'exemple Caddy est utilisable tel quel (`make docker-run-tls`) : testé via `docker compose -f docker-compose.tls.yml config`, qui valide la syntaxe et confirme que `PATCHCORD_DOMAIN` non défini échoue immédiatement avec un message clair plutôt qu'un Caddy silencieusement mal configuré.
- Aucun changement à `internal/` : le choix de ne rien construire ici est vérifié, pas supposé — pas de régression possible sur le comportement HTTP existant.
- La doc renvoie explicitement de "TLS" vers l'authentification admin, réduisant le risque qu'un opérateur expose publiquement une API encore non protégée en pensant que TLS seul suffit.

## Conséquences négatives
- Un déploiement interne/offline sans domaine public (nginx + certificats auto-signés ou fournis autrement) n'a pas d'exemple Compose prêt à l'emploi dans ce dépôt — seulement documenté en une phrase (`docs/book/src/cli/serve.md`) renvoyant au principe général. Un opérateur dans ce cas doit écrire sa propre configuration de reverse proxy.
- `caddy_data`/`caddy_config` sont des volumes Docker nommés, pas des montages liés visibles dans le dépôt comme `./data` — un opérateur qui veut sauvegarder/inspecter le certificat doit connaître `docker volume inspect`, une friction légèrement différente du reste de `docker-compose.yml`.
- Aucun test automatisé (CI) ne couvre cet exemple au-delà de la validation de syntaxe (`docker compose config`) faite pendant cette passe — un changement futur au `Caddyfile` ou au compose pourrait casser silencieusement l'obtention réelle du certificat sans qu'aucun test ne le détecte.
